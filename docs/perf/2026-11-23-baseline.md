# Gateway load baseline (laptop numbers)

Run on 2026-11-24. These are laptop numbers from one machine. They make no claim about production capacity.

## Machine
- MacBookPro18,1, 16 GiB RAM (17179869184 bytes), macOS 26.5.2 (25F84), OpenJDK 21.0.12.1 (Homebrew).
- Docker runtime: Colima, server 29.5.2, VM with 4 CPUs and 9.69 GiB memory.
- Everything ran on this one machine: ten services, Postgres, Kafka, Temporal, Mailpit, Prometheus, Jaeger, Grafana and the k6 container.

## Image tags
prom/prometheus:v3.5.0, jaegertracing/jaeger:2.23.0, grafana/grafana:12.2.0, grafana/k6:1.8.3 (verified on Docker Hub, pinned in dev/load/README.md).

## Sampling
Trace sampling was `TRACING_SAMPLING=0.1` for the load runs (the variable all ten services read; default is 1.0, used for the e2e sanity check).

## Exact commands
```
docker compose -f dev/docker-compose.yml up -d
docker compose -f dev/docker-compose.yml --profile observability up -d
./mvnw -DskipTests package
dev/up.sh && dev/e2e-observability.sh        # sampling 1.0, PASS
dev/down.sh && TRACING_SAMPLING=0.1 dev/up.sh
for SC in steady probe; do
  docker run --rm -v "$PWD/dev/load:/load" \
    -e BASE_URL=http://host.docker.internal:8080 -e IDP_URL=http://host.docker.internal:9100 \
    -e SCENARIO=$SC grafana/k6:1.8.3 run /load/gateway.js
done
```
Results: dev/load/results/2026-11-24T03-11-33-511Z.json (steady), dev/load/results/2026-11-24T03-11-35-623Z.json (probe). Not committed (git-ignored).
The sanity script needed a fix first: it queried Jaeger's v1 `/api/services`, which Jaeger 2.23 does not serve; it now uses `/api/v3/services` (separate commit).

## Where the time goes (slowest 1%, from Jaeger)
Queried `/api/v3/traces` for service `gateway` (sampling 0.1, so a sample: 671 traces, 5138 spans). Trace-level duration: median 21.9 ms, 99th percentile about 196 ms, max 820 ms. Slowest traces:
- 820 ms and 791 ms: gateway span (outbound HTTP GET ~400-425 ms) then shared-service `GET /v1/notifications/unread-count` ~306 ms, of which `security filterchain before` ~184 ms and `authenticate bearertoken` ~174 ms. The time is in bearer-token authentication in the downstream service.
- 310 ms: gateway call to auth-service `GET /.well-known/jwks.json` took 112 ms (JWKS fetch by a downstream or the gateway).
- 290, 235, 212 ms: auth-service `GET /v1/me`, with `security filterchain before` / `authenticate bearertoken` 31-104 ms and `secured request` 97-200 ms.
Reading: the tail is dominated by token authentication in the downstream services (JWT validation and JWKS fetch), not by the gateway itself or by database work. Only a handful of traces are in the slowest 1% at this sampling rate, so treat this as indicative.

steady: p95 of `http_req_duration{endpoint:gateway}` < 300 ms PASS (136.7 ms); `http_req_failed` < 1% PASS; `rate_limited_responses` == 0 PASS; `server_error_responses` == 0 PASS.
probe: `http_req_failed` == 0 PASS; `rate_limited_responses` >= 1 PASS (80); `retry_after_on_429` rate == 1 PASS; `server_error_responses` == 0 PASS.
All thresholds passed.

## Limits of this test
- One laptop, shared by the load generator, the ten services and all infrastructure; k6 competes for the same 16 GiB and CPU.
- One instance per service, no replicas, no load balancer.
- Local infrastructure (Postgres, Kafka, Temporal) in a 4 CPU Colima VM; no real network latency or TLS.
- Synthetic users from the dev identity provider; only two read endpoints.
- Rate-limit buckets are in memory in a single gateway.
- The probe's 429 count is expected behaviour (the rate limiter engaging), not an error.
- Tracing at 10% sampling; trace statistics come from a sample.
- Dev-only histogram setting: owner-decided percentile histograms are enabled in dev so the p95 dashboard panel has data; that is a dev setting, not a production recommendation.
- `COLLECTOR_OTLP_ENABLED` is still present in dev/docker-compose.yml (Jaeger v2 has OTLP on by default, so the variable is not needed there).
